## Proposed reconciliation strategy

1. **Repository source recovery, no staging SQL:** add immutable source files
   for every staging-only hotfix using the original remote ledger version and
   exact SQL. These files will not execute on staging because their versions
   are already in the remote ledger. This gives the repository a reproducible
   account of the schema/history.
2. **Proven version remap:** repair only the ledger entries listed in the first
   staging-only table: mark each obsolete staging version `reverted` and the
   functionally identical repository version `applied`. No migration SQL runs
   and no business table is changed.
3. **Proven unledgered effect:** mark only `20260806000811` applied after
   preserving evidence that `payments_stripe_session_id_key` already exists.
   No SQL runs and no table data changes.
4. **Leave genuine pending repository migrations pending:**
   `20260731132542`, `20260803203905`, `20260803230000`, and
   `20260809000001` are not ledger-repaired. They remain deployment work for
   the subsequent RC deployment phase.
5. Validate with `supabase migration list --linked`, schema checks, indexes,
   constraints, RLS state, and the pre/post row-count snapshot. Do not deploy
   the RC migration or any application component in this mission.

## Risks

- A ledger remap without the evidence above would conceal a failed migration;
  this plan does not do that.
- Staging-only function and trigger hotfixes must be recovered before any
  attempt to treat the repository as reproducible.
- The RC1 migration remains unapplied; field deployment remains blocked even
  after ledger reconciliation.
