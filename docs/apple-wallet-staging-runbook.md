## Apple Developer setup

### 1. Create the Pass Type ID

In Apple Developer → Certificates, Identifiers & Profiles → Identifiers → `+` → Pass Type IDs.

Recommended identifier:

`pass.ch.chargeurs.membership`

The final identifier chosen here must be used verbatim as `APPLE_PASS_TYPE_IDENTIFIER` and must match the Pass Type ID certificate.

### 2. Create the Pass Type ID certificate

In Apple Developer → Certificates → `+` → Services → Pass Type ID Certificate.

Create a CSR on the Mac that will retain the matching private key:

Keychain Access → Certificate Assistant → Request a Certificate from a Certificate Authority → enter email/common name → leave CA email empty → Save to disk.

Upload the `.certSigningRequest` file to Apple and download the resulting `.cer` certificate.

### 3. Preserve the matching private key

The private key generated by the CSR remains in macOS Keychain. The certificate alone is insufficient; the server needs the certificate plus its matching private key.

Install the downloaded `.cer` by opening it, then export the resulting certificate + private-key identity from Keychain Access as a password-protected `.p12` for the transfer step.

Treat the `.p12` and extracted key as signing credentials. Do not email them, commit them, or paste them into tickets/chat.

### 4. Convert certificate/key to PEM for the Edge Functions

Example on macOS with OpenSSL:

```bash
openssl x509 -inform DER -in chargeurs-wallet.cer -out chargeurs-wallet-cert.pem
openssl pkcs12 -in chargeurs-wallet.p12 -nocerts -nodes -out chargeurs-wallet-key.pem
```

The second command intentionally produces an unencrypted PEM key because the current APNs mTLS client loads the key directly from the Edge Function secret. Protect the file tightly and delete the temporary local export after the secret has been stored.

### 5. Obtain the correct WWDR intermediate certificate

Pass Type ID certificates currently use Apple's WWDR G4 intermediate certificate. Download the current G4 intermediate certificate from Apple's PKI / WWDR certificate page and convert it to PEM if needed:

```bash
openssl x509 -inform DER -in AppleWWDRCAG4.cer -out AppleWWDRCAG4.pem
```

### 6. Convert the PEM values to one-line Base64

On macOS:

```bash
base64 -i chargeurs-wallet-cert.pem | tr -d '\n'
base64 -i chargeurs-wallet-key.pem | tr -d '\n'
base64 -i AppleWWDRCAG4.pem | tr -d '\n'
```

Map them to:

- pass certificate → `APPLE_PASS_SIGNER_CERTIFICATE_BASE64`
- private key → `APPLE_PASS_SIGNER_KEY_BASE64`
- WWDR G4 → `APPLE_WWDR_CERTIFICATE_BASE64`

### 7. Set Team ID and authentication secret

Set `APPLE_TEAM_IDENTIFIER` to the Apple Developer Team ID associated with the Pass Type ID.

Generate the server-only HMAC secret locally:

```bash
openssl rand -base64 48
```

Store the output as `APPLE_WALLET_AUTH_SECRET`.

## Supabase secret activation

Use Supabase Dashboard → Edge Functions → Secrets and add the six values above. Do not store them in the repository or frontend environment.

No code redeploy is required only to make newly stored Edge Function secrets available; after saving them, use the Wallet sandbox configuration probe to verify that `configured` becomes true.

## Real iPhone validation

1. Sign in to the staging Chargeurs.ch account that has the real active Chargeurs+ membership.
2. Open `/compte/pass`.
3. Select `Tester Apple Wallet`.
4. Confirm that the Apple configuration state says signature is available.
5. On the iPhone, select `Ajouter à Apple Wallet`.
6. Accept the real Apple Wallet sheet.
7. Verify that exactly one real device registration appears in `customer_wallet_device_registrations`.
8. Run `Synchroniser les données réelles` without changing the backend. Expected: `changed = false`; pass revision must not increment.
9. Run `Tester le transport Wallet`. Expected: business values and pass revision stay unchanged; only the explicit Wallet update tag and APNs transport are exercised.
10. Make one legitimate staging Chargeurs+ change (for example a real staging rental/return event that already belongs to the test account), then synchronize. Expected: visible-data hash changes, pass revision increments exactly once, APNs is sent, and Wallet requests the new `.pkpass` with the same Pass Type ID + serial number.

## Acceptance rules

The test fails if any of the following occurs:

- a fabricated membership, rental, ChargePoint balance, credit, reward, device, or success state appears;
- `pass_revision` increments when visible backend data has not changed;
- a technical `updated_at` change alone causes Wallet to report changed business data;
- Wallet is shown as issued before a `.pkpass` has actually been signed and served;
- APNs success is claimed when no Apple device is registered or APNs rejected the notification;
- a private Apple signing credential appears in Git, browser code, logs, or a public URL.
